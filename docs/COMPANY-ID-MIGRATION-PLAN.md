# خطة عزل الشركات البنيوي — `CompanyId` على `Employee`

**التاريخ:** 2026-07-31 · **الحالة:** ✅ **المرحلة (أ) منفَّذة — التشخيص جرى والبيانات نظيفة**

## 0. نتائج التشخيص (شُغِّل على الإنتاج بواسطة المالك، 2026-07-31)

| الفحص | النتيجة |
|---|---|
| الشركات | **شركتان**: الأولى بها **1357 موظفاً**، الثانية **صفر** |
| موظفون بلا فرع صالح | **0** ✅ |
| فروع بلا شركة صالحة | **0** ✅ |
| تعارض شركة القسم مع الفرع | **0** ✅ |
| أقسام عابرة للشركات | **0** ✅ |
| مستخدمون يعملون عبر أكثر من شركة | **0** ✅ |
| استعلام أحجام الجداول (7) | فشل: `Invalid object name 'DayAttendance'` — اسم الجدول مختلف؛ **تقدير حجم لا أثر له على القرار** |

**قراءة النتيجة بصدق:** البيانات **نظيفة تماماً** ⟹ الترحيل بلا استثناءات ولا
تخمين. لكن الشركة الثانية **موجودة بلا موظفين** — أي أن النظام **مهيَّأ لتعدد
المستأجرين ولم يُشغَّل به فعلياً بعد**. وهذا يجعل الآن **أفضل توقيت ممكن**: نضيف
القيد قبل أن تدخل بيانات الشركة الثانية، لا بعدها.

## 1. لماذا الآن

تأكيد المالك (2026-07-31): **النظام يخدم أكثر من شركة فعلياً بالإنتاج اليوم.**
وهذا يحوّل الفجوة الموثّقة بـ`docs/COMPANY-ISOLATION-AUDIT.md` من «دَين معماري
مؤجَّل» إلى **خطر تسريب بين مستأجرين حقيقيين**.

## 2. الوضع القائم (فحص كود، لا فحص بيانات)

| الكيان | حامل الشركة | إلزامي؟ |
|---|---|---|
| `Employee` | ❌ **لا يحمل `CompanyId` إطلاقاً** | — |
| `Employee.BranchId` | — | ✅ `int` غير قابل للإفراغ |
| `Employee.DepartmentId` | — | ✅ `int` غير قابل للإفراغ |
| `Branch.CompanyId` | ✅ | ✅ `int` |
| `Department.CompanyId` | ✅ | ✅ `int` · و`BranchId` **قابل للإفراغ** |

**الخلاصة:** المسار `Employee → Branch → CompanyId` **مكتمل بالنموذج**، فالانتماء
مشتقّ لا مفقود. المشكلة أنه:

1. **غير مفروض بالمخطط** — أي استعلام يبدأ من `Employees` ولا يصل للفرع يفقد الحاجز.
2. **مصدران متنافسان** — الفرع والقسم يحملان `CompanyId` كلٌّ على حدة، ولا شيء
   بالمخطط يمنع اختلافهما لنفس الموظف.

## 3. ما لا أعرفه ولا أستطيع معرفته

الوصول لقاعدة الإنتاج ممنوع عليّ (`docs/AI-DEVELOPMENT-RULES.md`). لذا **لا أعرف**:

- كم موظفاً بلا فرع صالح (`BranchId = 0` أو فرع محذوف) — هؤلاء لا شركة لهم.
- هل توجد فروع بلا شركة صالحة.
- كم موظفاً شركةُ قسمه ≠ شركة فرعه (تعارض يحدّد أيّ المصدرين هو القاعدة).
- هل يعمل مستخدم باك أوفيس واحد عبر أكثر من شركة (يحدّد الحاجة لـ«شركة نشطة»).

**قبل كتابة أي هجرة يجب تشغيل:** `scripts/sql/company-isolation-diagnostics.sql`
(قراءة فقط، `SELECT` حصراً، بلا أي تعديل). نتائجه تحدّد الفروع الثلاثة أدناه.

## 4. المسار المقترح (بعد التشخيص)

### المرحلة أ — العمود والترحيل (هجرة محكومة)

1. `ALTER TABLE Employees ADD CompanyId int NULL` — **NULL أولاً** لا `NOT NULL`،
   فلا يفشل الترحيل على صفّ شاذّ واحد.
2. تعبئة: `UPDATE e SET CompanyId = b.CompanyId FROM Employees e JOIN Branches b …`
3. **تقرير ما بقي NULL** — لا نخمّن شركة موظف. يُعالَج يدوياً بقرار المالك.
4. `NOT NULL` + مفتاح أجنبي + فهرس **فقط بعد** أن يصبح المتبقّي صفراً — هجرة لاحقة
   منفصلة، لا نفس الهجرة.

### المرحلة ب — الفرض (تدريجي، لا دفعة واحدة)

بالأولوية: الموظفون ⟵ المستندات ⟵ الرواتب ⟵ الحضور ⟵ التقارير.
كل خطوة معها اختبار عزل بشركتين، على نمط `CompanyIsolationScopeTests` القائم.

### المرحلة ج — منع الانحدار

قيد على الكتابة: إنشاء/نقل موظف يجب أن يوافق `CompanyId` شركةَ فرعه، وإلا رفض
صريح. بلا هذا القيد يعود الانحراف بعد شهر.

## 5. قواعد ملزمة لهذا العمل

- **ممنوع تشغيل الهجرة على الإنتاج آلياً** — خطوة نشر صريحة بموافقة لكل مرّة.
- **ممنوع تخمين شركة موظف** — الصفّ الغامض يبقى NULL ويُعالَج بقرار بشري.
- **ممنوع ادّعاء «عزل بين الشركات»** قبل وجود اختبارات تُثبته على المسار المعني.
- كل خطوة قابلة للرجوع: العمود NULL لا يكسر أي كود قائم.

### تحقّق ما بعد النشر (شغّله بعد أول إقلاع)

```sql
SELECT COUNT(*) AS EmployeesWithoutCompany
FROM Employees WHERE IsDeleted = 0 AND CompanyId IS NULL;   -- يجب أن يكون 0

SELECT COUNT(*) AS DriftedRows
FROM Employees e JOIN Branches b ON b.Id = e.BranchId
WHERE e.IsDeleted = 0 AND (e.CompanyId IS NULL OR e.CompanyId <> b.CompanyId);  -- 0
```

**لا تُشدَّد `NOT NULL` قبل أن يرجع الاستعلامان صفراً.**
