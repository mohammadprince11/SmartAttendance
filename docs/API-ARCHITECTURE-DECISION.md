# قرار معماري — مضيف الـAPI

**التاريخ:** 2026-07-31 · **الحالة:** معتمد للإصدار الحالي

## السياق

بالمستودع مشروعان يمكن أن يستضيفا API:

| المشروع | الحالة الفعلية |
|---|---|
| `SmartAttendance.Web/Controllers/Api` | **الـAPI الحقيقي العامل**: مصادقة توكن Bearer (`ApiTokenAuthHandler`)، نقاط الموبايل، WebAuthn، Web-Push |
| `SmartAttendance.API` | **شبه فارغ** (9 ملفات، أغلبها قالب `Program.cs` وملفات مشروع) — لا نقاط أعمال |

بقاء الاثنين بلا قرار معلن يخاطر بتنفيذ متوازٍ: نقطة تُضاف هنا وأخرى هناك،
فينشقّ نموذج المصادقة والصلاحيات — وهو خطر أمني لا مجرد فوضى تنظيمية.

## القرار

**للإصدار الحالي:**

1. **`SmartAttendance.Web/Controllers/Api` هو المضيف النشط الوحيد للـAPI.**
2. **`SmartAttendance.API` لا يستقبل أي نقطة جديدة** حتى يُعتمد مشروع استخراج مخصص.
3. **لا يُحذف `SmartAttendance.API`** بهذه المهمة: هو ضمن الحل وقد تعتمد عليه
   إعدادات/سكربتات، والحذف يحتاج تحقّقاً مستقلاً من انعدام التبعيات وتبريراً معلناً.
4. وُضع `SmartAttendance.API/README.md` كعلامة تمنع التنفيذ المتوازي بالخطأ.

## المبرر

- الـAPI العامل مرتبط بطبقة المصادقة والصلاحيات والوصول للبيانات داخل `Web`؛
  استخراجه الآن يعني نسخ أو إعادة بناء تلك الطبقة — عمل كبير بمخاطر أمنية.
- لا قيمة تشغيلية فورية من الفصل بالحجم الحالي.
- الأولوية الحالية لإصلاحات الأمان والحوكمة، لا لإعادة الهيكلة.

## شروط إعادة النظر لاحقاً

يُعاد فتح القرار عند تحقّق أحد هذه:

- حاجة لتوسيع/نشر الـAPI مستقلاً عن الويب.
- عملاء خارجيون يحتاجون عقداً وإصداراً منفصلين.
- حاجة لحدود أمنية أو شبكية منفصلة.

عندها يكون الاستخراج **مشروعاً مستقلاً** بخطة ترحيل واختبارات تكامل ونسخ عقود،
لا نقلاً تدريجياً للملفات.
