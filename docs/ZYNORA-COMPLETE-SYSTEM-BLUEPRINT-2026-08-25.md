# المخطط الشامل لنظام ZYNORA HR

**الحالة:** مرجع التنفيذ الرسمي  
**التاريخ:** 2026-08-25  
**النطاق:** المنتج، تجربة الاستخدام، المعمارية، الصلاحيات، التكاملات، الاختبارات والتشغيل  
**مرجع الواجهة الملزم:** `docs/design-system-v1.md`

## 1. الرؤية

ZYNORA منصة HR عربية متكاملة تجعل سجل الموظف مصدراً واحداً للحقيقة، وتربط دورة العمل كاملة:

`الموظف ← العقد والهيكل ← الجدول والحضور ← الإجازة/الإذن ← المخالفة/الإضافي ← الراتب ← البنك والمحاسبة ← التقارير`

المنتج موجه أولاً للعربية وRTL، يعمل لشركة واحدة أو مجموعة شركات، ويعزل بيانات كل شركة ونطاق كل مستخدم في الاستعلام نفسه.

## 2. مبادئ المنتج

1. **مهمة أولاً:** الصفحة تبدأ بما يجب على المستخدم فعله، لا بكثرة القوائم.
2. **مصدر حقيقة واحد:** لا تكرار لكيان الموظف أو تعريف البند المالي أو الوردية.
3. **أثر قابل للتفسير:** كل احتساب أو تغيير أو موافقة يمكن تفسيره وتدقيقه.
4. **آمن افتراضياً:** المعرّفات غير موثوقة، وعزل الشركة ونطاق الموظف مفروضان بالخادم.
5. **إعادة آمنة:** عمليات الاستيراد والاحتساب والمزامنة والكتابة تراعي idempotency والمعاملات.
6. **لا حماية وهمية:** لا يظهر إعداد أو صلاحية أو فلتر غير منفذ فعلياً.
7. **لا صفحة صامتة:** تحميل، فراغ، خطأ، نجاح، منع صلاحية وتعطيل موضحة دائماً.
8. **التهيئة قبل التخصيص البرمجي:** السياسة والقواعد والقوالب قابلة للإدارة من النظام.

## 3. بنية التنقل

تتكون القائمة الرئيسية من سبعة مراكز ثابتة:

1. **الرئيسية:** مهامي، التنبيهات، مؤشرات اليوم، الإجراءات السريعة.
2. **الأشخاص:** الموظفون، الهيكل، العقود، الوثائق، الأصول، التغييرات والتقارير.
3. **الوقت:** الحضور، الورديات، الجداول، الطلبات، المعالجة، المخالفات والتقارير.
4. **الإجازات والخدمة الذاتية:** الطلبات، الأرصدة، التقويم، السياسات والموافقات.
5. **الرواتب:** المدخلات، التشغيل، التدقيق، الاعتماد، الملفات البنكية، المحاسبة والتقارير.
6. **التفاعل:** الإعلانات، المهام، النماذج، الاستبيانات والإقرارات.
7. **الإدارة:** الشركات، الصلاحيات، مسارات الموافقة، الإعدادات، التكاملات، التدقيق والأداء.

القشرة العامة تضم بحث `Ctrl+K`، مبدل الشركة المصرح بها، مهام الموافقة، الإشعارات، اللغة، المظهر، والمساعدة السياقية.

## 4. عقد الواجهة الموحد

كل صفحة تُصنف في واحد من أربعة أنماط: قائمة إدارية، تفاصيل سجل، شبكة تفاعلية، أو إعدادات.

الترتيب القياسي:

`breadcrumb → page header → primary action → KPIs ≤ 4 → filters → content → pagination`

### المكونات الإلزامية

- `zy-page-header`: عنوان، وصف قصير، زر أساسي واحد.
- `zy-filter-bar`: بحث سريع، فلاتر أساسية، و`details` للفلاتر المتقدمة.
- `zy-table-wrap`: أعمدة قابلة للفرز، اختيار جماعي، تصدير وصلاحيات إجراءات.
- `zy-empty`, `zy-skeleton`, `zy-error`: حالات واضحة.
- `zy-badge`: نص ونقطة/أيقونة؛ لا معنى يعتمد على اللون وحده.
- `zy-drawer`: التفاصيل الكبيرة وسجل النشاط.
- `zy-modal`: عملية قصيرة لا تتجاوز حقولاً قليلة.
- `data-zyconfirm`: كل كتابة خطرة أو غير قابلة للتراجع.
- `zy-toast`: نتيجة العملية مع رقم مرجعي عند الحاجة.

ممنوع CSS داخل الصفحة، والألوان المباشرة، واتجاهات `left/right`، ومكونات بديلة تؤدي نفس الوظيفة.

## 5. وحدة الأشخاص

### الملف 360

- الهوية والعمل والاتصال.
- العقد والحركة الوظيفية.
- الراتب والبيانات البنكية حسب صلاحية الحقل.
- الوثائق والانتهاء والتنبيهات.
- الأصول والعهد.
- الحضور والإجازات والطلبات.
- الخط الزمني والتدقيق.

### العمليات

- إنشاء موظف عبر wizard: هوية → وظيفة → عقد → مالية → وثائق → حساب → مراجعة.
- استيراد جماعي: ملف → مطابقة أعمدة → معاينة → أخطاء → تأكيد → نتيجة قابلة للتنزيل.
- Onboarding/Offboarding بقوالب مهام ومسؤولين ومواعيد.
- حركة وظيفية مؤرخة لا تعدل الماضي: نقل، ترقية، مدير، قسم، راتب، إعادة توظيف.
- طلب تعديل بيانات مع السابق والجديد ومسار اعتماد.

### قواعد القبول

- لا رقم موظف مكرر داخل الشركة.
- كل سجل تابع يتحقق من `CompanyId` ونطاق الموظف.
- الحقول الحساسة مخفية من المصدر والاستجابة، لا من CSS فقط.
- كل تغيير مؤثر ينتج Audit Event قابل للبحث.

## 6. الوقت والحضور

### خط المعالجة

`مصدر البصمة → تطبيع → مطابقة الموظف والشركة → إزالة التكرار → تطبيق الجدول → تطبيق الاستثناءات → حساب الدلالات → توصية/طلب → اعتماد → إغلاق الفترة → تصدير الراتب`

### الوظائف

- ورديات عادية وليلية ومرنة وعابرة لمنتصف الليل.
- roster أسبوعي/شهري وتعيين جماعي واستثناء فردي مؤرخ.
- بصمة جهاز/ويب/جوال مع المصدر والموقع والثقة.
- طلب بصمة ناقصة وتعديل يدوي مع سبب ومرفق وتدقيق.
- إجازة، مهمة، عمل من المنزل، عطلة ورمضان كاستثناءات ذات أولوية محددة.
- إعادة احتساب بنطاق واضح ومعاينة أثر قبل التنفيذ.
- إغلاق فترة يمنع التعديل إلا بإعادة فتح مصرح بها ومسجلة.

### قواعد القبول

- لا حساب مزدوج لنفس الحدث.
- المنطقة الزمنية والتوقيت الصيفي وعبور منتصف الليل مختبرة.
- أي تعديل يعيد احتساب الموظف/اليوم المتأثر فقط ما لم يطلب نطاق أكبر.
- التصدير للراتب لا يقرأ فترة غير معتمدة.

## 7. الإجازات والخدمة الذاتية

- سياسات استحقاق وترحيل وانتهاء وحدود سالبة قابلة للتهيئة.
- يوم كامل، نصف يوم، وساعات.
- منع التداخل مع إجازة/مهمة/جدول حسب السياسة.
- تقويم فريق يحترم خصوصية النوع.
- بديل موظف وتسليم مهام.
- إلغاء يعكس الرصيد والأثر التشغيلي بصورة ذرية.
- بيع/تسوية رصيد ضمن الرواتب بصلاحية واعتماد مستقلين.

الحالة القياسية للطلب:

`Draft → Submitted → InReview → Approved/Rejected → Applied → Cancelled/Reversed`

## 8. محرك الموافقات

المحرك عام ويستخدمه الموظفون والحضور والإجازات والرواتب والمالية:

- خطوات متسلسلة أو متوازية.
- شروط حسب الشركة، القسم، الدور، النوع، القيمة أو الحقل المتغير.
- منع self-approval.
- تفويض مؤقت بمفعول زمني.
- SLA، تذكير، escalation وبديل.
- إعادة للطالب للتعديل.
- Snapshot لتعريف المسار وقت التقديم كي لا تغير الإعدادات طلباً جارياً.
- سجل قرار: الفاعل، الوقت، التعليق، النسخة، والنتيجة.

## 9. الرواتب

### دورة التشغيل

`فتح الفترة → استيراد/اشتقاق المدخلات → Preflight → Simulation → إنشاء المسير → مقارنة وانحرافات → مراجعة → اعتماد → إغلاق → بنك → محاسبة → نشر القسائم`

### الوظائف

- بنود معرفة بمعرف ثابت، نوع، خضوع ضريبي/تأميني، وصلاحية زمنية.
- إضافات واستقطاعات ثابتة ومتغيرة وحدود شهرية.
- أثر الحضور والإجازة والإضافي بعد اعتماد المصدر.
- Off-cycle وRetroactive كمسيرات منفصلة قابلة للتسوية.
- مقارنة الشهر السابق وقواعد كشف الشذوذ.
- قسيمة قابلة للتفسير تعرض أساس كل بند ومصدره.
- قوالب بنك ذات إصدار والتحقق من IBAN والصفوف غير القابلة للتحويل.
- قيود محاسبية متوازنة وتوزيع مركز تكلفة.
- إغلاق غير قابل للتعديل؛ التصحيح بمسير عكسي/تكميلي.

### فصل الواجبات

معدّ المدخلات، مشغّل المسير، المراجع، المعتمد، ومصدّر البنك أدوار منفصلة قابلة للتهيئة. لا يجوز لمستخدم واحد تجاوز الفصل إلا بدور طوارئ مسجل.

## 10. الصلاحيات والعزل

الصلاحية ناتج أربعة أبعاد:

`Feature Permission × Company Scope × Employee Data Scope × Sensitive Field Policy`

- Feature: عرض/إنشاء/تعديل/حذف/اعتماد/تصدير/إغلاق.
- Company: شركة واحدة أو مجموعة مصرح بها.
- Employee: الذات، المرؤوسون، القسم، الفرع، قائمة مخصصة أو الكل.
- Field: الراتب، البنك، الهوية، الوثائق، البيانات الطبية.

كل Page Handler وAPI endpoint يدخل مصفوفة صلاحيات آلية. لا يعتمد الأمان على إخفاء الزر.

## 11. التقارير والتحليلات

- Catalog موحد بتعريف الاسم، المصدر، الحقول، الصلاحيات والحساسية.
- فلاتر وتجميع وفرز وأعمدة محفوظة للمستخدم.
- Excel/PDF/CSV بعقد تصدير موحد.
- جدولة وإرسال مع إعادة فحص الصلاحية وقت التنفيذ.
- Drill-down من KPI إلى الصفوف المكونة له.
- تعريف مركزي للمؤشرات: الغياب، التأخير، turnover، تكلفة الرواتب، headcount.

## 12. التكاملات

- API حقيقية في `SmartAttendance.Web/Controllers/Api` بإصدارات واضحة.
- Webhooks موقعة، قابلة لإعادة المحاولة، وذات idempotency key.
- موصلات أجهزة الحضور مع heartbeat وdead-letter queue.
- بنوك وERP ومحاسبة عبر adapters، لا شروط موزعة داخل الصفحات.
- SSO وSCIM اختيارياً للمؤسسات.
- لا سر في المستودع؛ الأسرار من secret provider مناسب للبيئة.

## 13. المعمارية المستهدفة

- `Domain`: قواعد نقية لا تعتمد على Web أو SQL.
- `Application`: use cases وحدود معاملات وسياسات التخويل.
- `Infrastructure`: EF/SQL، الملفات، التكاملات، jobs والـobservability.
- `Web`: presentation فقط، ولا يملك منطق أعمال أو DDL وقت التشغيل.
- Query services تعيد DTOs محددة ولا تحمل جداول كاملة للترشيح بالذاكرة.
- الكتابات الحرجة تستخدم transaction وunique constraints وidempotency.
- تغييرات المخطط بهجرات محكومة قابلة للمراجعة والرجوع التشغيلي.

## 14. التشغيل

- Health endpoints منفصلة: liveness وreadiness.
- OpenTelemetry للـtraces والmetrics والlogs مع Correlation ID.
- Data Protection keys مشتركة و`ApplicationName` ثابت.
- Distributed lock للهجرات والjobs والعمليات المجدولة.
- تخزين ملفات خاص مشترك مع فحص malware واستخدام روابط قصيرة العمر.
- SQL retry للقراءة الآمنة فقط أو ضمن سياسة تراعي idempotency.
- نسخ احتياطي، استعادة، RPO/RTO واختبار كوارث دوري.

## 15. استراتيجية الاختبار

### بوابة كل PR

- Unit tests لمنطق المجال.
- Authorization/tenant tests لكل handler وendpoint معدل.
- Integration tests على SQL Server للتعاملات والقيود والتزامن.
- Snapshot/contract tests للتقارير والتصديرات.
- Accessibility وRTL smoke للصفحات المعدلة.

### بوابة الإصدار

- Playwright: الدخول، الموظف، الحضور، الإجازة، الموافقة، المسير، البنك والقسيمة.
- Tenant A/B denial matrix.
- 10k employee performance baseline.
- استعادة نسخة احتياطية وتجربة migration.
- تدقيق الحزم والأسرار ورفع/تنزيل الملفات.

## 16. مراحل التنفيذ

### المرحلة 0 — الأساس

- تصفير أخطاء البناء ومعالجة تحذيرات nullability عالية المخاطر.
- تشغيل SQL acceptance بصورة موثوقة خارج الإنتاج.
- جرد حيّ لكل stub و`قريباً` وصلاحية غير منفذة.
- توحيد shell والمكونات وإيقاف إضافة CSS إصلاحي جديد.

### المرحلة 1 — الأشخاص والموافقات

- ملف 360 وwizard الإنشاء والحركات المؤرخة.
- محرك الموافقات العام ومصفوفة الصلاحيات.
- استيراد الموظفين وOnboarding/Offboarding.

### المرحلة 2 — الوقت والإجازات

- pipeline الحضور، إغلاق الفترات، المصمم الأسبوعي/الشهري.
- ربط الإجازة والمهمة والعمل من المنزل والحضور.
- اختبارات الورديات الليلية والتزامن والاستيراد.

### المرحلة 3 — الرواتب

- ربط المصادر، simulation والانحرافات وفصل الواجبات.
- إغلاق الفترة، off-cycle/retro، البنك والمحاسبة.
- Golden tests وتفسير القسيمة.

### المرحلة 4 — التقارير والتكاملات

- report catalog/builder، الجدولة، التصدير وdrill-down.
- موصلات البنك/ERP/الأجهزة وAPI/Webhooks.

### المرحلة 5 — الجاهزية

- E2E شامل، أداء، عزل شركات، accessibility، مراقبة وتعافٍ.
- لا إعلان «جاهز 100%» إلا بعد أدلة البوابة وتوقيع قبول المالك.

## 17. تعريف الاكتمال

لا تعد الميزة مكتملة لمجرد وجود الصفحة. الاكتمال يعني:

1. المتطلبات وحالات الحافة موثقة.
2. الصلاحيات وعزل الشركة والموظف مفروضان بالخادم.
3. واجهة RTL متجاوبة بكل الحالات.
4. الكتابة ذرية وآمنة عند الإعادة.
5. اختبارات unit/integration/E2E المناسبة خضراء.
6. التدقيق والمراقبة لا يكشفان بيانات حساسة.
7. لا stub ولا زر وهمي ولا فلتر غير منفذ.
8. البناء وتدقيق الحزم و`git diff --check` خضراء.

## 18. سياسة التسليم

- فرع مستقل لكل دفعة.
- Draft PR مع وصف أثر الأعمال والأمن وقاعدة البيانات والاختبارات.
- لا دفع مباشر إلى `main` ولا دمج ذاتي.
- لا نشر ولا وصول إلى إنتاج دون موافقة صريحة للعملية نفسها.
