# قواعد التطوير بالذكاء الاصطناعي — ZYNORA HR

**مصدر الحقيقة الوحيد** لكل أدوات الـAI العاملة على هذا المستودع (Claude، Codex،
أي وكيل مراجعة). `CLAUDE.md` و`AGENTS.md` يشيران إلى هذا الملف ولا يناقضانه.

النظام يدير بيانات موارد بشرية حقيقية لأكثر من 1300 موظف: رواتب، حضور، إجازات،
قروض، وثائق شخصية. الخطأ هنا يمسّ أشخاصاً ومالاً — القواعد أدناه **إلزامية**.

## 1. الفروع والدفع

- **ممنوع الدفع المباشر لـ`main`** إطلاقاً.
- فرع واحد لكل مهمة: `agent/<وصف-قصير>` أو `feature/<وصف>`.
- افتح **Draft Pull Request** — لا دمج بلا مراجعة.
- **ممنوع النشر** بلا موافقة صريحة **لهذه العملية بالذات**؛ موافقة سابقة لا تُعمَّم.
- ممنوع الوصول لبيانات الإنتاج أو تعديل قاعدة بيانات الإنتاج.

## 2. الأمان والخصوصية

- ممنوع وضع بيانات اعتماد/توكنات/سلاسل اتصال/أسرار/عناوين إنتاج بالمستودع.
- ممنوع وضع بيانات موظفين حقيقية (أسماء، رواتب، أرقام وطنية، وثائق، حسابات بنكية)
  بالكود أو الاختبارات أو التوثيق.
- **ممنوع تسجيل** كلمات المرور، التوكنات، الرواتب، الأرقام الوطنية، المستندات
  الشخصية، أو تفاصيل البنوك بأي سجلّ.
- ممنوع تخزين ملفات الموظفين الخاصة تحت مسار ثابت عام (`wwwroot`) — تُخزَّن بمجلد
  محمي وتُخدَم عبر نقطة مصادَقة تتحقق من الصلاحية والنطاق.

## 3. الصلاحيات وعزل البيانات

- **كل** استعلام عن بيانات موظف يجب أن يفرض نطاق التخويل (لا تحميل بالمعرّف وحده).
- **كل** استعلام متعدد الشركات يجب أن يفرض عزل `CompanyId`.
- كل معرّف قادم من المسار/النموذج/الكويري = **غير موثوق** حتى يُتحقق من ملكيته
  ونطاقه (منع IDOR).
- ممنوع «جلب الكل ثم الترشيح بالذاكرة» — الترشيح بالاستعلام.

## 4. مجالات الأعمال الحرجة

أي تعديل يمسّ **الرواتب، الحضور، الإجازات، القروض، الشؤون المالية** يتطلب:

- اختبارات انحدار للمنطق النقي قبل الدمج.
- توثيق الأثر بوصف الـPR.
- **ممنوع تغيير صيغ الرواتب أو حسابات الحضور أو أرصدة الإجازات** إلا بطلب صريح
  أو كإصلاح أمني مؤكَّد وموثَّق.

## 5. قاعدة البيانات

- تغييرات المخطط عبر **هجرات محكومة**: EF Core للكيانات المُدارة، وسكربتات SQL
  مُصدَّرة للجداول القديمة الخام.
- **ممنوع إضافة جدول أو عمود جديد عبر كود الشفاء الذاتي وقت التشغيل**
  (`EnsureCreatedAsync` وأخواته) — راجع `docs/RUNTIME-SCHEMA-INVENTORY.md`.
- الهجرات تعمل صراحةً، تفشل بوضوح، ولا تعمل مع كل طلب، ولا تُطبَّق تلقائياً بالإنتاج.

## 6. عمليات الكتابة

كل عملية كتابة يجب أن تراعي: إعادة المحاولة، الإرسال المكرر، المعاملات
(transactions)، والـidempotency. الحفظ المزدوج بطلب مالي أو بصمة = خطأ حقيقي.

## 7. تقسيم الأدوار بين الوكلاء

- **يجوز للوكيل الذي يعيّنه المستخدم صراحةً وكيلاً منفّذاً أن ينفّذ** التطبيق
  والاختبارات ضمن حدود طلب المهمة الحالي.
- **الوكيل المعيّن للمراجعة يبقى للقراءة والمراجعة فقط** ولا ينفّذ.
- **طلب المهمة الحالي هو الذي يحدّد دور الوكيل النشط**؛ ولا توجد أفضلية دائمة
  لمورّد أو اسم وكيل بعينه.
- **ممنوع أن يعدّل وكيلان نفس شجرة العمل في الوقت نفسه** — استخدم فرعاً/شجرة عمل
  منفصلة أو انتظر انتهاء الآخر.

## 8. الحفاظ على المنتج

- الحفاظ على سلوك العربية RTL وهوية ZYNORA البصرية.
- ممنوع حذف وظيفة قائمة بلا توثيق السبب بالـPR.
- التصميم يتبع `docs/design-system-v1.md`.

## 9. Graphify

- شغّل `graphify update .` بعد تعديل الكود عند توفره.
- **اعتبر مخرجات Graphify بائتة** إذا كان كوميت مصدرها لا يساوي `HEAD` — لا تبنِ
  قراراً على رسم قديم؛ حدّثه أو تحقق من الكود مباشرة.

## 10. التحقق قبل أي PR

```bash
dotnet restore SmartAttendance.slnx
dotnet build SmartAttendance.slnx -c Release --no-restore
dotnet test SmartAttendance.Tests/SmartAttendance.Tests.csproj -c Release --no-build
dotnet list SmartAttendance.slnx package --vulnerable --include-transitive
git diff --check
```

E2E يعمل على بيئة اختبار مخصصة فقط — **ممنوع على الإنتاج**، وممنوع الاختبارات
المدمِّرة. إذا نقصت متصفحات Playwright فأبلغ عن المتطلب بدل إخفاء الفشل.
